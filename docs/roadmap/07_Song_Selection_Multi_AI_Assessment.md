# RodiO 选歌模块：多 AI 评估意见整合底稿

> 本文档整合了九份来自不同 AI 的评估意见（DeepSeek × 2、Cyrus/Gemini、Kimi、腾讯元宝 × 2、Evan/GPT、Qwen、豆包），供后续架构讨论和开发决策参考。
>
> 评估基于《RodiO 选歌模块技术披露》文档，时间：2026-06-04。

---

## 一、各方意见核心摘要

### 1. DeepSeek（工程方案）

**核心判断：** 当前架构最大问题是 LLM 同时承担"发现"和"决策"两个职责，导致两条路径各自的缺点被放大。

**建议架构：三层漏斗**

| 层 | 职责 | 实现方式 |
|---|---|---|
| 候选生成层 | 多源召回，不依赖 LLM 判断 | Spotify 搜索、Last.fm 相似、本地歌单时段加权、网易云推荐 |
| 精排层 | 对候选列表做审美排序与过滤 | LLM（DeepSeek）读取 taste.md + 上下文 + 候选列表（≤200首），输出 Top N |
| 队列组装层 | 连贯性、去重、黑名单、冷却、重试 | 规则引擎 + 轻量情绪过渡检查 |

**关键主张：**
- LLM 只做"策展"，不做"搜索/生成"，解析失败率 → 0
- 路径 A / B 合并为一条：候选生成 → LLM 精排 → 入队
- 播放连贯性：在精排 prompt 中要求输出 `energy_level` 和 `mood` 字段，后置差值检查，差值 >2 触发调整
- 声学特征替代：放弃实时特征，使用 Last.fm 标签 + 人工映射情绪能量表
- Skip 信号：捕捉跳过行为，分析 `(track_penalty + artist_penalty * 0.3 + tag_penalty * 0.5 + scene_penalty)` 的综合惩罚

---

### 2. DeepSeek（激进方向）

**核心判断：** 当前架构即使完美实现，本质仍是"推荐"而非"共情"。应让电台不再是"选择歌曲"，而是"创造体验"。

**五个激进方向：**

**① 声景实时合成**
- 不再从库中选歌，根据实时上下文用生成模型（AudioLDM 2、MusicGen、Suno API）合成音乐
- 妥协方案：80% 时间从库中选歌，20% 时间插入 1-2 分钟 AI 合成声景过渡
- 风险：音质艺术性不足，生成延迟高

**② DJ 实时干预音乐**
- DJ 不只是在歌曲间说话，而是对正在播放的歌做实时处理
- 能力：声轨叠加（叠加环境音）、段落跳切（智能选择打断时机）、用户请求时实时施加 DSP 效果
- 技术：需要从 Spotify Web Playback SDK 切换到 Web Audio API 自行解码路由

**③ 简化 Bandit（强烈推荐）**
- 不做完整 RL，只做上下文 Bandit：LLM 给出 K 个候选，系统随机选择一个，观察反馈，更新权重
- 实现极其轻量（几十行代码），效果可能超出预期

**④ 共情监听器**
- 被动感知用户状态：打字节奏、鼠标轨迹、麦克风环境音
- 前端用 TensorFlow.js 运行轻量模型，压缩成几个特征值发给后端
- 隐私：本地处理 + 用户明确授权

**⑤ 动态品味画像（强烈推荐）**
- 每周有 2% 概率播一首背离画像的歌，观察反应
- 不跳过 → 品味扩展；跳过 → 强化原有边界
- 维护多个子画像（工作模式/深夜模式/运动模式），在线切换

**最快见效的激进组合（3 周内可实现）：**
1. 动态品味画像（修改 50 行代码 + 每天日志分析）
2. DJ 最简实时干预（前端 Web Audio + 预置音效，自动叠加环境音过渡）
3. 简化 Bandit（精排后候选 epsilon-greedy 探索，记录跳过率）

### 3. Cyrus / Gemini（向量检索方案）

**核心判断：** 应从"推荐"演进为"向量检索 + LLM 重排"的漏斗架构。

**建议架构：**

```
[ 11,732 首本地曲库 + 外部发现库 ] 全量向量化
               ↓
[ 向量检索层 ]
  → 依据当前环境快照的文本 Embedding，盲检出前 200 首最贴合的曲目
               ↓
[ LLM 审美品味重排（DeepSeek）]
  → 将 200 首（含元数据、标签、歌词摘要）喂给 DeepSeek
  → 挑出 10-15 首，规划播放顺序（同时解决连贯性）
```

**关键主张：**
- 用 LLM 对曲库进行离线结构化打标，使用符合 taste.md 的内敛标签（`[冷调夜色]`、`[雨水冲刷]`、`[清晨微光]`）
- 运行时将环境快照转化为语义词，通过标签/向量初步锁定边界，再由 DeepSeek 决定"此刻对的那首歌"
- 路径 B 不再是盲目随机抽 50 首，而是语义相关的候选池

**局限：** 需要先完成曲库打标工作，否则 embedding 质量很低。

### 4. Kimi（漏斗级联 + 扩库思路）

**核心判断：** 路径 A（自由生成）是"先射箭后画靶"，路径 B（随机抽 50 首）是"低质量利用"，两条路径的 LLM 都不该生成具体歌名。

**路径重构：**

路径 A → 探索（Exploration）：
```
LLM 生成"审美意图描述"：
{ mood, texture, reference_artists, avoid }
→ 意图送入检索系统（MusicBrainz/Last.fm/Spotify 搜索）
→ 验证可播放性后进入待审核新曲池
```

路径 B → 深耕（Exploitation）：
```
取消"随机抽 50 首"
→ 向量检索 Top-K（当前上下文 → 查询向量 → 库内检索 100 首）
→ LLM 从 100 首中选 15 首（已有 Spotify URI，无需搜索）
```

**扩库三层机制：**

| 方法 | 说明 |
|---|---|
| Spotify Related Artists | `/artists/{id}/related-artists` 端点**尚未关闭**，从核心艺人出发做拓扑，抓取二度关联艺人的 Top Tracks |
| 编辑策展源 | 接入 Pitchfork、Resident Advisor、Bandcamp Daily 的 RSS，用 LLM 过滤符合 taste.md 的推荐 |
| LLM 跨文化映射 | "用户喜欢 Nujabes，华语圈类似的有什么？" → 艺人名 + 理由 → 验证可播放性 |

**发现流水线：**
```
1. 每周从 MusicBrainz 图谱 + 编辑源 + LLM 跨域提名收集候选（50-100 个）
2. LLM 初筛（读取艺人介绍、风格描述，判断是否匹配 taste.md）
3. Spotify 验证可播放性，获取 URI
4. 进入"试听池"（不直接推，等待检索命中）
5. 用户播放未跳过 → 加入正式曲库并打标签
```

### 5. 腾讯元宝（工程架构 + 腾讯生态）

**核心判断：** 保留双路径但调整职责分工，路径 A 负责审美判断，路径 B 负责安全播放。

**建议调整：**
- 路径 A 输出改为：情绪锚点（如"深夜/内省/低动态"）+ 推荐歌单 + 禁止风格
- 路径 B 变为执行层：在路径 A 定义的情绪区间内抽样，不做审美判断
- 路径 B 候选池改为：先基于场景数据 + 近期播放 + taste.md 用 LLM 筛出 200 首，再随机缩至 50 首

**场景数据处理：**
- 将环境快照先通过规则引擎转化为"场景标签"（如"芒种-潮湿沉郁"、"新月-内省"）
- 再注入 LLM prompt，强化场景与选曲的绑定

**腾讯生态建议（个人项目参考价值有限）：**
- 混元大模型替代 Qwen，支持 128K 上下文，可完整载入 taste.md
- QQ 音乐 `getSimilarSongs` 替代 Last.fm
- TME 音频标签 API 自动标注情绪字段
- 火山引擎 VKE 替代 Railway 部署

### 6. 腾讯元宝 / 字节视角（火山引擎生态）

与腾讯元宝内容高度重叠，主要推火山引擎产品栈（Skylark 模型、ByteHouse、VKE）。

**有参考价值的独立观点：**
- 支持模型微调：基于 taste.md + 用户播放记录构造微调数据集，让模型深度对齐审美原则（技术方向值得关注，不限于字节生态）
- 路径 B 候选池生成应该升级：先基于场景+taste.md 筛选 200 首，再随机缩至 50 首进入受限选择

### 7. Evan / GPT（最贴近代码现实的方案）

**核心判断：** 问题不是"架构方向错了"，而是缺少中间层。当前把审美判断、场景解释、曲目生成、连贯性控制、失败兜底都交给 LLM 一次性完成，质量自然飘。

**最核心的改法：LLM 生成 mood intent，而非歌名**

```json
{
  "scene": "深夜独处 / 新月 / 微潮湿 / 不宜太甜",
  "target_mood": ["introspective", "misty", "restrained", "textural"],
  "avoid": ["bright indie pop", "EDM drop", "over-sentimental ballad"],
  "energy_range": [0.25, 0.45],
  "vocal_density": "low_to_medium",
  "language_preference": ["Japanese instrumental", "art pop", "Mandarin restrained vocal"],
  "transition_strategy": "from current track slowly darker, no sudden tempo jump"
}
```

**四层架构：**

```
1. 场景理解层
   时间 / 天气 / 月相 / 用户输入 / 最近播放 → mood intent JSON

2. 候选召回层（分层召回）
   - 40 首：当前时段高匹配曲
   - 25 首：与当前播放曲相近
   - 20 首：近期未播放但历史高亲和
   - 20 首：扩展库新发现
   - 10 首：低风险探索曲
   - 5 首：反直觉但可能惊喜

3. 排序过滤层
   taste 匹配度 / 场景匹配度 / 新鲜度 / 可播放性 / 连贯性 / 反馈惩罚

4. 播放叙事层
   生成 say / segue / DJ 串讲，不暴露算法感
```

**播放连贯性（轻量实现）：**

为每首歌建立分值：
```json
{
  "energy": 0.32,
  "brightness": 0.28,
  "density": 0.41,
  "tempo_feel": 0.35,
  "vocal_presence": 0.55,
  "emotional_weight": 0.72
}
```

```
transition_cost =
  |energy_a - energy_b| * 0.30
+ |brightness_a - brightness_b| * 0.20
+ |density_a - density_b| * 0.15
+ |tempo_feel_a - tempo_feel_b| * 0.15
+ |emotional_weight_a - emotional_weight_b| * 0.20
```

规则：深夜 transition_cost ≤ 0.25，白天工作流 ≤ 0.35，每 5-7 首允许一次"反差曲"但需 DJ 串讲解释。

**Skip 信号分层（最完整的设计）：**

| 行为 | 判断 | 权重 |
|---|---|---|
| 0-20 秒内跳过 | 强负反馈 | -3 |
| 20-60 秒跳过 | 中负反馈 | -2 |
| 播放超过 70% | 弱正反馈 | +1 |
| 播放完整 | 正反馈 | +2 |
| 重播/加入收藏 | 强正反馈 | +4 |
| 用户手动点歌 | 场景强正样本 | +5 |
| TTS 后立刻跳过 | 单独记录（可能是串讲失败） | — |

Skip 惩罚逻辑：
```
skip_penalty = track_penalty + artist_penalty * 0.3 + tag_penalty * 0.5 + scene_penalty
```
深夜跳过明快 indie pop ≠ 讨厌这首歌，而是"深夜/新月/低能量场景下不适合"，要区分场景惩罚与歌曲惩罚。

**扩库三路：**
1. Last.fm `track.getSimilar` + `artist.getSimilar`（track similar 为空时用 artist 扩展）
2. LLM 语义提名（基于当前曲 + taste.md + 场景意图提名"气质相近但不显然"的曲目）
3. 建立 `discovery_candidates` 池（验证→低频试播→沉淀为 `validated_tracks`）

**新曲比例建议：**
```
普通时段：70% 已验证库 + 20% 久未播放旧收藏 + 10% 新发现
探索时段：50% 已验证库 + 25% 久未播放 + 25% 新发现
```

### 8. Qwen（元数据增强 + 血统溯源）

**核心判断：** 不要让 LLM 直接生成歌名，而是让它输出"目标特征向量"，由检索系统在向量库中做相似度搜索。

**元数据增强层：**
- 用 MusicBrainz / Cyanite.ai / 开源声学分析工具对曲库进行特征提取
- 提取维度：情绪值（内省/明快）、能量值（低/高）、流派标签、器乐占比、人声质感
- 存入向量数据库（ChromaDB 或 SQLite 向量扩展）
- 改造选歌流程：LLM 输出"目标特征向量" → 系统在向量库检索 Top-K → 直接入队

**血统溯源扩库（独特视角）：**
- 制作人/合作人网络：利用 MusicBrainz 查询制作人，挖掘同制作人的其他作品（制作人审美往往稳定，如梁翘柏制作的陈奕迅）
- 厂牌/子厂牌：查询歌曲所属厂牌，挖掘同厂牌下其他冷门但风格一致的艺人
- 语义 + 声学双重验证：LLM 给出"风格描述" → 搜索新歌 → 声学特征必须与种子歌单特征距离在阈值内才入库

### 9. 豆包（综合工程实现）

**核心判断：** RodiO 不应该是"LLM 帮你选歌"，而应该是"一个有审美意图的本地音乐系统，LLM 只负责理解此刻和表达温度"。

**最终推荐架构：**

```
用户输入 / 天气 / 时间 / 天文 / 当前曲
        ↓
Scene Interpreter（DeepSeek）→ Mood Intent JSON
        ↓
Candidate Recall（分层召回）
        ↓
Candidate Scoring（多维打分）
- taste_score / scene_score / freshness_score
- continuity_score / feedback_score / playability_score
        ↓
Queue Builder
- 控制曲风比例 / 新旧比例 / 相邻跨度 / 探索比例
        ↓
DJ Narration
- say / segue / 不解释算法，只解释感受
```

**短期最值得做的 6 个改进（优先级排序）：**
1. 增加 `track_profile` 标签表（LLM 批量打标，不需要第三方声学 API）
2. 路径 B 随机 50 首 → 分层召回 120 首
3. 增加 skip / complete / replay 事件记录
4. 增加 `transition_cost` 简单分值控制相邻曲跨度
5. 路径 A 改为 LLM 生成意图 + 少量自由提名（每批 20 首中：16 首已验证 + 2 首 Last.fm + 2 首 LLM 提名）
6. 建立 `discovery_candidates` 池，新曲发现从主链路拆出

**实施路线图：**

| Phase | 内容 | 周期 |
|---|---|---|
| Phase 1 | 标签化与规则引擎（曲库打标、情绪跨度检查、路径 B 改造） | 1-2 周 |
| Phase 2 | LLM 角色重构（路径 A 改意图生成、统一"候选池→LLM排序→验证"流程） | 2-3 周 |
| Phase 3 | 库扩展流水线（MusicBrainz 图谱、编辑源、试听池机制） | 持续运行 |
| Phase 4 | 负反馈闭环（skip 信号分层、跳过数据注入 context） | 1 周 |
| Phase 5 | 模型替换验证（Qwen → DeepSeek，用固定场景对比评估） | 1 周 |

## 二、跨方案共识（所有 AI 均认可）

1. **LLM 不应直接生成歌名**，应改为生成"审美意图/mood intent"，由工程层做候选检索和验证
2. **候选池生成要结构化**，不能随机抽 50 首，需要基于场景+时段+历史做分层召回
3. **本地标签体系是所有改进的地基**，没有标签，向量检索和连贯性控制都无法实现
4. **Skip 信号必须捕捉并利用**，是系统自我进化的关键负样本
5. **播放连贯性用轻量规则解决**，不需要复杂声学分析，transition_cost 函数足够
6. **Spotify `/recommendations` 和 `/audio-features` 已永久关闭**，不可依赖

## 三、各方分歧与争议点

| 争议点 | 分歧内容 |
|---|---|
| 向量检索的时机 | Cyrus/Kimi/Qwen 主张用 embedding 做语义检索；DeepSeek/Evan 认为先打标签再说，向量检索是第二步 |

| 动态品味画像 | DeepSeek 激进文档强烈推荐；其他方案未涉及 |
| 腾讯/字节生态 | 元宝和字节推自家产品，对个人项目实用性存疑，其他方案均未推荐 |

## 五、Soren 的综合判断

### 最关键的一个决策

**路径 A 的 LLM 是否继续"直接生成歌名"，还是改为"生成 mood intent"。**

这是整个系统的分水岭。改了这一个点，解析失败率、幻觉、不稳定性会显著改善，且不需要重写整个架构。

### 优先级排序

**立即可做（不需要新的基础设施）：**
1. 路径 A 改为 LLM 生成 mood intent JSON，工程层做候选检索和验证
2. 路径 B 的"随机抽 50 首"改为分层召回（按时段/历史亲和度/新鲜度分层）
3. 增加 skip 事件记录（0-20秒/20s-2min/70%+ 三个阈值）

**中期（需要一次性预处理工作）：**
4. 曲库打标签（LLM 批量标注，每首歌打 mood/energy/texture/vocal_density 等字段）——这是所有后续改进的地基
5. Spotify Related Artists 离线扩库（一次性脚本，从 taste.md 核心艺人做拓扑）
6. 增加 transition_cost 控制相邻曲情绪跨度

**长期（有了标签体系之后）：**
7. 向量检索替代标签过滤
8. 动态品味画像（2% 探索比例 + 画像自动更新）
9. 编辑策展源接入（Pitchfork RSS + LLM 过滤）
10. 简化 Bandit 优化精排权重

### 不建议做的

- 声景实时合成：艺术性不足，与 RodiO 核心诉求冲突
- 共情监听器（摄像头/麦克风）：隐私成本过高，现阶段干扰多于帮助
- 腾讯/字节生态接入：个人项目过重，接入门槛不合适
- 完整 RL 系统：数据稀疏，一个人的电台样本量不够
